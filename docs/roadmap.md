## 0. 一句话

**本地算力是固定成本，云端 token 是边际成本。所以先用可执行的验证器把本地算力用满，仍然过不去时再按最小粒度向云端"买建议"，买过的建议写成教训卡，同类问题不买第二次。**

框架不绑定 benchmark：任何能提供"验证器阶梯"的任务都能接入。数学、代码、论文分析各做一个示例，在同一引擎上和"固定大模型 agent"比云端花费、时间、完成度。

## 1. 问题设定

| 项目 | 设定 |
|---|---|
| 云端强模型 | 硅基流动 API（OpenAI 兼容），按 token 计费 |
| 本地弱模型 | 租用 RTX 4090（24GB）+ vLLM 部署开源模型，按小时计费 |
| 任务 | 三大类各一个示例：数学优化、代码、论文分析 |
| 对照对象 | 固定大模型 agent：（a）同一引擎全程用云端模型；（b）现成框架 DeerFlow 原生 + 固定云端模型 |
| 指标 | 完成度（验证器给分）、成本（云端 ¥ + 本地 GPU 折算 ¥）、端到端墙钟时间 |

**和已有工作最实在的区别在计费结构。** FrugalEvo、LEVI、ShinkaEvolve 里的"便宜模型"多是按 token 计费的 API，多试一次就多花一份钱。我们的弱模型在租来的 GPU 上，租金已经付了，多试一次只花时间。于是取舍从"强模型 vs 弱模型"变成"云端的钱 vs 墙钟时间"，这正是评委看的两个数。

## 2. 框架总览

```
任务(ResearchTask) ──► 控制器(纯代码)
                          │
        ┌─────────────────┼──────────────────────┐
        ▼                 ▼                      ▼
  本地执行器          验证器阶梯             决策菜单
  vLLM, K 路并行      L0 → L1 → L2          教训命中 / 加宽 / 提示 /
  (固定成本)          (纯代码, 给证据)       诊断 / 重规划 / 接管 / 停止
        │                 │                      │
        └────────► 决策账本(JSONL) ◄─────────────┘
                          │
                    教训库(只收已验证的)
```

控制流全部由代码决定，LLM 只填内容。小模型不负责"决定下一步干什么"，这样本地模型弱一点也不会把流程带偏。

## 3. 五个机制

### 3.1 统一任务接口 + 验证器阶梯（通用性的来源）

```python
class ResearchTask:
    goal: str                 # 研究目标
    workspace: Path           # 初始代码 / 数据 / 论文
    ladder: list[Verifier]    # L0 便宜 → L2 昂贵
    budget: Budget            # 云端 ¥ 上限、时间上限
    def state_card(self) -> str   # 压缩状态，≤600 tokens
    def failure_signature(self, results) -> str   # 失败的归类键
```

| 级别 | 作用 | 数学 | 代码 | 论文分析 |
|---|---|---|---|---|
| L0 | 能不能跑 | 程序可执行、输出格式对 | 可编译 / 可导入 | 输出符合 JSON schema |
| L1 | 对不对 | 约束合法（不重叠、不越界） | 可见测试 + 性质测试 | 每条引文必须在原文里逐字找到 |
| L2 | 好不好 | 目标函数值 | 隐藏输入正确性 + 加速比 | 答案与标准答案比对 |

L0、L1 对所有候选都跑，L2 只对通过 L1 的前几名跑。验证资源本身也按价值分配。

所有决策只看验证器给出的证据，不看模型的自评置信度。新任务类别只要实现这个接口就能接入，这是"通用"的定义。

### 3.2 本地饱和优先：K 路并行投机

- 每一步让本地模型**并行生成 K 个不同候选**（不同温度、不同提示角度），vLLM 连续批处理下 K 个请求的墙钟远小于 K 倍。
- 验证器筛选，取最好的继续。
- K 自适应：连续有提升就减半（省时间），全部失败先加倍一次再考虑升级。
- 论文任务里同样适用：分块并行抽取证据，云端永远不读全文。

依据：自托管推理的单位成本强烈依赖并发。有工作测得单流服务比饱和时贵 1.9 倍；另一项企业案例把"并行生成候选 + 测试过滤，利用本地零边际成本"列为未来工作。我们把它做出来并测量。

### 3.3 咨询阶梯：云端按"建议粒度"分级购买

传统级联是"弱模型失败 → 强模型接管整步"。我们把云端调用拆成四档，从便宜到贵逐级爬：

| 档 | 云端看到什么 | 输出上限 | 作用 |
|---|---|---|---|
| 提示 Hint | 状态卡（目标、当前最优、失败签名） | ≤150 tokens | 给一个方向 |
| 诊断 Diagnose | 状态卡 + 最小失败样例 / 报错 | ≤400 tokens | 指出错因 + 一条可复用规则 |
| 重规划 Replan | 状态卡 + 实验日志摘要 | ≤800 tokens | 换一组方案 |
| 接管 Takeover | 完整上下文 | 不限 | 云端亲自做这一步 |

每次咨询后必须回到本地至少跑一轮，验证有提升才算有效；无效才爬下一档。输入一律是本地压缩过的状态卡，系统提示固定放最前以命中前缀缓存。

设计动机：输出 token 单价通常是输入的数倍，接管最贵。若多数卡点在"提示"档就能解决，云端花费会比直接接管低一个量级（待测）。

### 3.4 教训卡摊销：买过的建议不买第二次

每次云端咨询生成一张结构化教训卡：

```json
{"signature": "circle_packing/overlap_after_local_opt",
 "task_class": "math", "rung": "diagnose",
 "advice": "……", "condition": "n≥20, 用了梯度法后处理",
 "verified_delta": 0.031, "cost_cny": 0.004, "uses": 0}
```

- **只有验证器确认带来提升的建议才入库**，并记录成立条件。未经验证的经验不进记忆。
- 升级前先按失败签名检索教训库，命中就注入本地提示重试，不花云端的钱。
- 可测指标：同类任务序列中，第 n 个任务的云端花费、升级被避免的比例。

这回应赛题的"可持续提升"和主办方 comment4 的"agent 能否自我迭代"。

### 3.5 统一价格表 + 时间价值旋钮 α

把所有动作放进一张价格表，用同一个单位（元）比较：

```
price(a) = 云端¥(a) + (ρ_gpu + α) × 耗时(a)
```

- `ρ_gpu`：4090 租金（元/秒）。报告里两种口径都给：计入租金、视为沉没成本。
- `α`：用户愿意为节省一分钟付多少钱。**α 是唯一的旋钮**：α→0 时系统尽量本地多试（省钱、慢），α 大时更早升级（快、贵）。扫 α 就得到成本–时间–完成度的前沿曲线。

决策规则（MVP 版本）：

```
每轮:
  cands   = local.propose(state, K)          # 一次 batch
  results = ladder.run(cands)                # L0/L1 全跑, L2 跑前 m 名
  if 有提升:  记账; K = max(K_min, K//2); continue
  sig = task.failure_signature(results)
  if lessons.hit(sig):   注入教训; continue          # 免费
  if 尚未加宽 and price(加宽) < price(提示):  K *= 2; continue
  rung = 下一档(提示→诊断→重规划→接管)
  if 剩余预算 < price(rung) or 近 R 次咨询的 Δ/¥ 低于阈值:  停止
  consult(rung); 回到本地
```

加分项（时间够再做）：用账本里的实际 Δ 更新每档的期望收益，让阶梯顺序自适应。

### 3.6 决策账本

每个动作记一行 JSONL：

```json
{"run":"math-01","step":7,"action":"hint","trigger":"stagnation(3)",
 "cloud_in":412,"cloud_out":96,"cloud_cny":0.0041,"gpu_s":0,"wall_s":3.2,
 "score_before":2.581,"score_after":2.604,"verified":true,"lesson_id":"L-012"}
```

用途：前端回放、每档 ROI、事后找出"白花的升级"和"该升没升"两类失误（EcoAgent-Bench 的视角）、计算 BA-AUC。预算上限由控制器硬性执行，不依赖模型自觉。

## 4. 三个示例任务

| 类别 | 任务 | 完成度定义 | 单次上限 |
|---|---|---|---|
| 数学 | 单位正方形内放 26 个圆，最大化半径和。agent 写程序产出布局 | 合法性门槛 × 半径和 / 文献最好值 | 10 分钟 |
| 代码 | 给一个慢的 Python 函数（如批量相似度 Top-K）和测试，要求优化 | 正确性门槛 × 加速比（多次计时取中位数，与基线交替运行） | 10 分钟 |
| 论文分析 | 给 2–3 篇论文全文，回答 12 道题，每个答案附原文引文 | 答案正确率 × 引文可核验率 | 10 分钟 |

说明：

- 圆形装填是 AlphaEvolve、ShinkaEvolve、FrugalEvo 都用过的任务，结果能和文献对照。文献最好值约 2.635 是我凭记忆写的，写进报告前请核对原文。
- 代码任务在 CPU 上计时，不和本地模型抢 GPU。
- 论文题目和标准答案由队友人工准备（数字、短事实为主，加 2 道综合题）。综合题的最终评分用云端模型盲评，这部分评测花费单独记，不计入 agent 成本。
- 每类先做一个任务。有余力时每类加到 3 个，用来测教训摊销。

## 5. 与已有工作的关系（新颖性的诚实定位）

每个机制单看都有前作，不能说"首个"。

| 我们的机制 | 最近的前作 | 差别 |
|---|---|---|
| 弱模型执行、卡住时咨询强模型 | Anthropic advisor tool（2026-04）；FrugalEvo；LEVI | advisor 由执行模型自己决定何时咨询；我们由控制器依据验证器证据决定，且分四档 |
| 本地并行多试 + 验证器 | Resample or Reroute?；Correct First, Fast Second（本地 7B + best-of-n）；企业编码 agent 经济学论文（列为未来工作） | 前者是单次查询层面或单一任务；我们把"加宽"和"升级"放进同一张价格表做取舍 |
| 强模型的建议沉淀复用 | Inter-Cascade（问答级联里的策略库）；EvoScientist（科研记忆） | 我们只收验证器确认有效的建议，并用它**跳过升级** |
| 按预算决定何时升级 | Budget-Aware Agentic Routing、SeqRoute（需训练路由器） | 我们免训练、规则可解释，动作空间含"不调任何模型" |
| 规划在云端、执行在本地 | Minions、HybridFlow、Specialize Roles Mix Deployments | 我们是研究闭环（假设–实验–验证–修正），不是单次问答或固定角色 |

**可以对外说的定位**：把咨询式强弱协作、本地并行投机、已验证教训复用整合进一个任务无关、由验证器驱动的控制器，并在"本地固定成本 + 云端边际成本"的真实计费结构下系统测量。

## 7. 演示模板：选 DeerFlow 2.0

**结论：用 DeerFlow 2.0，但只把它当外壳和对照，不把我们的控制器塞进它的 agent 循环。**

理由：

1. MIT 许可；Next.js 前端 + FastAPI Gateway + LangGraph agent harness，自带线程历史、Plan 模式、工具调用与子 agent 进度的流式展示、文件上传、Artifacts 面板、token 用量显示。
2. 模型在 `config.yaml` 里用 LangChain 类路径配置，硅基流动走 `langchain_openai:ChatOpenAI` + `base_url` 即可。
3. 扩展点齐全：自定义工具（`@tool`）、技能（SKILL.md）、中间件（`extensions.middlewares`）。
4. **它本身就是一个"固定大模型 agent 框架"**，配上固定云端模型可以直接当现成框架的对照组。

适配方式（我的判断）：

| 层 | 做法 |
|---|---|
| 引擎 | TierLab 是独立 Python 包，不依赖 DeerFlow，命令行可单独跑实验 |
| 接入 | 封装成 DeerFlow 自定义工具：`start_research(task, policy, budget)` 返回 run_id，`get_research_status(run_id)` 查进度；配一个 skill 说明何时调用 |
| 展示 | 引擎把账本和图表（前沿图、宽度曲线、决策回放 HTML）写到线程的 outputs 目录，由 Artifacts 面板预览 |
| 对话层 | DeerFlow 的 lead agent 用一个便宜的云端模型，只负责接单和汇报，它的花费单独记 |

不走 GPT 建议的"中间件里逐次换模型"路线，原因有二：那是逐步路由的范式，而我们的决策单位是"验证器反馈后的一个研究动作"；并且它要求本地模型能稳定驱动 DeerFlow 的工具调用循环，风险高。

未核实、今晚要冒烟的点：

- 长时间运行的工具调用在 DeerFlow 里会不会超时（所以设计成后台任务 + 轮询）。
- 文档只确认了 token 用量显示，没提费用显示。费用以我们自己的账本为准。
- GPT 给的启动命令和 Ollama 配置我没有逐条核对，以仓库 README 为准。
- 不要把带命令执行能力的服务暴露到公网。

备选：如果 DeerFlow 今晚 2 小时内跑不起来，退回"引擎 + 一个静态 HTML 看板"，演示不受影响。

## 8. 模型与部署

| 角色 | 选择 | 说明 |
|---|---|---|
| 云端强模型 | 硅基流动上的旗舰档（如 DeepSeek-V4-Pro） | 定价页列的是输入 ¥12、输出 ¥24、缓存 ¥1（每百万 token），另有来源称分时段计价。以开跑当天定价页为准，写进账本配置 |
| 本地模型 | 30B 级 MoE 通用模型的 4-bit 量化（Qwen3.6-35B-A3B 或 Qwen3-30B-A3B） | 硅基流动上有同款 API 价（Qwen3.6-35B-A3B 输入 ¥1.8、输出 ¥10.8），正好做 H5 |
| 本地备选 | 14B 级通用模型 | 24GB 上 30B 级权重占掉大半显存，KV cache 不够时并发上不去，换小模型换并发 |
| 推理服务 | vLLM（不用 Ollama） | 并行 K 路依赖连续批处理 |
| 上下文 | 本地 16K 起步 | 发给本地的都是压缩后的状态卡或论文分块 |

今晚必须实测的三个数：本地模型在 K=1/4/8 下的总吞吐（token/秒）、按指定格式输出 diff 和 JSON 的成功率、显存余量。这三个数决定 K 的上限和要不要换模型。

## 9. 实验设计

**对照组（同一引擎、同一工具、同一任务输入，只换策略）**

| 代号 | 策略 | 目的 | 优先级 |
|---|---|---|---|
| B0 | 全云端（固定大模型） | 主对照 | 必做 |
| B2 | 全本地 | 本地能力边界 | 必做 |
| B3 | 传统级联：本地失败 N 次后云端直接接管 | 证明阶梯、加宽、教训有用 | 必做 |
| Ours | 完整系统 | — | 必做 |
| A1 | Ours 去掉加宽（K=1） | H2 | 必做 |
| A2 | Ours 去掉教训库 | H4 | 尽量做 |
| B4 | 固定分工：云端规划 + 本地执行 | 对应 FrugalEvo / Minions 式分工 | 尽量做 |
| B1 | DeerFlow 原生 + 固定大模型 | 现成框架参照 | 有空再做 |

B1 和我们的引擎不是同一个 harness，只能当参照，不能当因果对比。主结论必须建立在 B0 上。

**指标**

- 完成度：各任务验证器给分，归一化到 0–1。
- 成本：云端 ¥（实际 token × 单价，含缓存）；本地 GPU 秒 × 租金。两者分列，再给合计。
- 时间：端到端墙钟。
- 过程指标：BA-AUC（完成度对累计云端花费的曲线下面积）、升级次数与各档占比、每档 ROI、教训命中率。

**规模**：必做的 5 组 × 3 任务 × 3 个种子 = 45 次，每次上限 10 分钟。全云端组不占 GPU，可以并行跑；用本地模型的组要串行，否则计时互相干扰。报告均值和波动范围，不挑最好的一次。

**α 扫描**：Ours 在 3 个 α 值上各跑一遍，画前沿曲线。时间不够就只在数学任务上扫。

## 11. 风险

| 风险 | 应对 |
|---|---|
| 示例任务太少，结论被质疑是挑出来的 | 任务和种子事先固定并写进仓库；报告波动范围；明确说是"每类一个示例"而非 benchmark 结论 |
| 云端单价低，绝对花费只有几分钱，对比不直观 | 报告比例和 BA-AUC，并折算成每千个任务的花费 |
| 本地模型格式不稳，拖慢迭代 | 约束解码（JSON schema）、小动作空间、连续格式错误先重采样再升级 |
| 24GB 显存下并发上不去 | 换 14B 级模型；K 上限按实测定 |
| 论文任务的验证器较弱 | 引文逐字匹配是硬约束；答案以短事实为主；综合题单独评分并说明 |
| 代码计时噪声 | 多次计时取中位数、与基线交替运行、加速比低于噪声带的不算提升 |
| 比赛规则 | 主办方答疑说 agent 模型由主办方提供。改用硅基流动前，确认是否允许、云端花费按什么口径统计 |
| DeerFlow 适配耗时超预期 | 引擎独立可跑，演示有静态看板兜底 |
